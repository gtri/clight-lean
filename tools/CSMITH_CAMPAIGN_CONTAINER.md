# Long CSmith Campaign Container

`Dockerfile.csmith-campaign` creates the self-contained environment used for a
deterministic CSmith differential-testing campaign. It builds CSmith locally
from a pinned public checkout and builds public CompCert plus the committed
Lean `clightgen` patch; it does not install either tool into a system prefix.

## Pinned inputs

The Dockerfile validates these pinned inputs:

| Input | Revision |
| --- | --- |
| CLight-Lean | pinned by `CLIGHT_LEAN_REV` in `tools/build-csmith-campaign-image.sh` (the single source of truth; the default image tag is derived from it) |
| CompCert upstream | `https://github.com/AbsInt/CompCert.git` at `96e66b844a839464d90c6e14bb97a4198832b50b` (public master snapshot after v3.17) |
| CompCert Lean backend | `patches/compcert-lean-clightgen.patch` (SHA-256 validated by the Dockerfile) |
| CSmith upstream | `https://github.com/csmith-project/csmith.git` at `0cdc710315cfee9035e22ef4363ca479270d1934` |
| Lean | `leanprover/lean4:v4.34.0` |
| Elan bootstrap | `v4.2.1` (`x86_64-unknown-linux-gnu` SHA-256 verified) |
| Container base | `ubuntu@sha256:1e0a86e57d247923571b75e0aaf48a1449cf8c543d51fb3e07a4a7d7bfa79316` |

From a checkout that contains the pinned `CLight-Lean` revision, use the
supplied builder. It exports that exact revision into a temporary source-only
context and invokes Docker without sending generated cases, artifacts, local
Lake caches, or unrelated untracked workspace material. The pin lives in
exactly one place — `CLIGHT_LEAN_REV` in the builder — and the default image
tag `clight-csmith:<short-hash>` is derived from it, so bumping the pin is a
one-line change:

```bash
tools/build-csmith-campaign-image.sh
```

To validate only the builder's source-only context assembly, without invoking
Docker or starting a container build, use:

```bash
CSMITH_CAMPAIGN_DRY_RUN=1 \
  tools/build-csmith-campaign-image.sh
```

The builder requires this repository's Git object database to contain the
pinned CLight-Lean commit; its current checkout and working-tree changes do
not enter the exported source archive. It copies only the current container
Dockerfile, entrypoint script, and CompCert patch as explicit WIP build inputs.
The image obtains CompCert and CSmith directly from their public upstream Git
repositories at the full pinned object IDs. It applies the committed patch with
`git apply --check` before building CompCert from source using Ubuntu 24.04's
Coq 8.18, OCaml, and Menhir packages.

The Lean backend patch is generated by `git diff --full-index` from the public
base `96e66b844a839464d90c6e14bb97a4198832b50b` to the tip of the CompCert
`lean-clightgen` branch (currently `8860f12c`, which adds the float-literal
change on top of `d469e2218614ee987424e55f90903f6ae2ac74f4`). The image uses
that public base—not the older `v3.17` tag—because it is the precise commit on
which the patch applies cleanly. The Dockerfile verifies the patch's SHA-256
before applying it, then checks it with `git apply --check`.
The Dockerfile defaults to two build jobs for CompCert and CSmith to avoid an
unbounded proof-build memory spike. To use a different bounded setup parallelism
on a prepared machine, invoke the Dockerfile directly with explicit values for
`COMPCERT_BUILD_JOBS` and `CSMITH_BUILD_JOBS`; do not use an unbounded
`$(nproc)` expansion by default.
The current image targets an x86-64 Linux campaign host, matching the pinned
CompCert `x86_64-linux` tools and the Lean `x86_64` execution instance.

## Run a campaign

Bind-mount the three ignored output roots. Do not bind-mount over the source
tree: the image has already built the pinned Lean dependencies and CompCert
tools it needs.

```bash
# Derive the image tag from the pinned revision (the builder's default).
rev=$(sed -n 's/^CLIGHT_LEAN_REV=//p' tools/build-csmith-campaign-image.sh)
image=clight-csmith:$(git rev-parse --short "$rev")

mkdir -p campaign-output/artifacts campaign-output/generated campaign-output/build

docker run --rm \
  --user "$(id -u):$(id -g)" \
  --mount type=bind,src="$PWD/campaign-output/artifacts",dst=/campaign/CLight-Lean/artifacts/csmith \
  --mount type=bind,src="$PWD/campaign-output/generated",dst=/campaign/CLight-Lean/GeneratedCases \
  --mount type=bind,src="$PWD/campaign-output/build",dst=/campaign/CLight-Lean/.csmith-diff-build \
  "$image" \
  --count 1000 \
  --seed-start 1 \
  --run-id paper_day1_seed1
```

The image entrypoint invokes `tools/csmith_corpus.py` with its pinned CSmith
binary, generated runtime headers, and sibling CompCert/CSmith roots. Add any
normal corpus-runner options after the image tag, for example:

```bash
  --timeout-seconds 30
```

The `--user` setting keeps the retained output host-owned. Omit it only when
root-owned output files are acceptable on the host.

## Parallel shards and resource control

`csmith_corpus.py` intentionally runs one seed at a time. To consume many CPU
hours, run independent containers over non-overlapping seed intervals. Keep
each worker's three output mounts and `--run-id` distinct; the corpus runner
intentionally refuses to overwrite an existing run or case namespace.

The generated-case Lake build can be memory-intensive. Constrain workers by
CPU affinity rather than launching unrestricted containers that each see every
host CPU. This is a conservative two-core worker example:

```bash
worker=0
seed_start=$((1 + worker * 1000000))
out="$PWD/campaign-output/worker-$worker"
mkdir -p "$out/artifacts" "$out/generated" "$out/build"

docker run --rm \
  --user "$(id -u):$(id -g)" \
  --cpuset-cpus 0-1 \
  --memory 16g \
  --mount type=bind,src="$out/artifacts",dst=/campaign/CLight-Lean/artifacts/csmith \
  --mount type=bind,src="$out/generated",dst=/campaign/CLight-Lean/GeneratedCases \
  --mount type=bind,src="$out/build",dst=/campaign/CLight-Lean/.csmith-diff-build \
  "$image" \
  --count 1000000 \
  --seed-start "$seed_start" \
  --run-id "paper_worker_${worker}_seed_${seed_start}" \
  --timeout-seconds 30
```

Choose disjoint CPU sets and seed intervals for other workers. Treat the
two-core/16-GiB values as a conservative starting point, not a measured host
requirement: run a small multi-worker pilot first, then increase worker count
only while memory pressure and case-build time remain acceptable.

## Resume and replay

To resume a stopped run, reuse exactly its output mounts and run ID:

```bash
docker run --rm ... "$image" \
  --count 1000 --seed-start 1 --run-id paper_day1_seed1 --resume
```

Each retained case has a `replay.sh` script in its artifact directory. It is a
diagnostic replay command for the recorded source and creates a fresh artifact
namespace; execute it inside a shell started from the same image with the
relevant output mounts available.

## Interpretation

The corpus exit summary uses `FAIL` for any non-`PASS` retained classification.
With the current profile, `TRANSFORM_REJECTED` union-valued function
parameter/return cases are expected CompCert ABI exclusions, not Lean/native
output mismatches. Separate them from `OUTPUT_MISMATCH`, `LEAN_STUCK`,
`LEAN_UNSUPPORTED`, native failures, and timeout outcomes in reported metrics.
